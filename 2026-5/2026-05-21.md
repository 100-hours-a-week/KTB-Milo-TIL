# 상태와 연결

# stateful vs stateless

- 상태를 기억하는 여부로 구분
- statfull
    - 장점
        - 맞춤형 서비스 가능
        - 복잡한 흐름 제어 가능
        - 게임, 채팅 등에서 사용
    - 단점
        - 서버가 상태를 계속 기억해야 함
            - memory라는 비싼 자원을 많이 써야함
        - 사용자가 많아지면 부담
        - 분산 시스템에서 처리가 힘듬
    - 예시
        - 게임 서버, DB 세션, WebSocket
- stateless
    - 장점
        - 서버 부담이 적음
        - 확장하기 편리함
        - 처리 속도가 빠름
    - 단점
        - 복잡한 요청에 보낼 정보가 많음
        - 사용자별 서비스가 어려움
            - 요청마다 필요한 정보를 전달해야 하고
            - 상태 유지가 필요한 기능은 별도 저장소(Session, DB, Token 등)가 필요하기 때문
        - 순서가 있는 경우라면 관리가 어려움
    - 예시
        - HTTP API, REST API

## Connection oriented vs Connectionless

- 연결 지속 여부로 구분
- Connection oriented
    - 전화
    - 연결 계속해서 유지
- Connectionless
    - 문자
    - 연결 유지x
- 전통적인 HTTP의 특징 = Connectionless + Stateless
- 현대 HTTP(1.1 Keep-Alive, HTTP/2, HTTP/3)는 연결 재사용하지만 애플리케이션 관점에서는 Stateless

## 인증, 인가

### 인증

- 사용자가 누구인지 확인
- 예시
    - 로그인
    - 토큰 검증

### 인가

- 인증된 사용자가 특정 자원에 접근할 권한이 있는지 확인
- 예시
    - 관리자 권한 확인
    - 게시글 수정 권한

## 쿠키, 세션

### 쿠키

- 브라우저(클라이언트)에 저장되는 작은 데이터
- 브라우저가 요청 시 자동 전송
- 사용자 상태 유지에 사용
- 예시
    - 로그인 유지
    - 언어 설정
    - 장바구니

주의

- 민감 정보 직접 저장은 위험

### 세션

- 상태를 서버에 저장
- 브라우저에는 Session ID만 저장되는 경우가 많음

# 프레임워크와 라이브러리

## 프레임워크(일관성)

- 기본적인 구조, 규칙, 기능을 정의한 것
    - 속도가 빨라지고 일관된 방식으로 만들 수 있게 됨
- 애플리케이션의 구조와 실행 흐름을 제공
- 프레임워크가 개발자 코드를 호출하는 구조
- 자율성(자유도) 낮지만 일관성 높음
- 자바 컬렉션 프레임워크

## 라이브러리(전문성)

- 재사용 가능한 기능 집합
- 개발자가 필요한 시점에 호출
- 특정 분야의 전문적인 것
- 복잡한 기능 구현 대신 가져와서 사용
- 빠른 개발과 높은 완성도를 가져갈 수 있다.
- 자율성(자유도) 높음
- socket.io

## API

- 두 객체 사이의 소통을 위해 사용하는 규약(설명서)
- 기능 호출 방법과 데이터 형식을 정의
- 시스템 간 데이터 교환 및 기능 공유 가능
- API를 통해서 이미 만들어진 다른 어플리케이션과 상호 작용이 가능
- 서로 다른 시스템이나 애플리케이션 간에 데이터를 교환하고 기능을 공유

### 표현 방식

## 사용자 표현 방식

#### 페이지 베이스 방식

- 페이지 번호 기반 조회

```java
GET /posts?page=3&size=20
```

- 1페이지, 2페이지… 같이 페이지 단위로 구분하는 방식

### 커서 베이스 방식

- 마지막 조회 위치(cursor) 기반 조회

```java
GET /posts?cursor=100
```

#### token-based

- 커서 베이스 방식에서 커서를 구현할때 토큰 형태로 인코딩하는 방식

## UI 표현 방식

#### 인피니티 스크롤

- 스크롤이 맨 아래 부분에 도착했을 때 , 다음 페이지를 요청하는 방식
- Page-based 사용 가능
- Cursor-based 사용 가능
- 실무에서는 Cursor + Keyset 조합 많음
- UI 패턴

## DB구현 방식

#### offset-based

- 몇 개 건너뛰고(offset) 가져올지 정하는 방식
- 장점
    - 구현이 간단
- 단점
    - 데이터가 많으면 느려짐
    - 데이터 변경이 많으면 중복, 누락이 생김

#### keyset based

- 마지막 조회 위치 기준(마지막 데이터 키 기준)으로 다음 데이터 가져오는 방식
- 장점
    - 큰 데이터에서도 조회 속도가 빠름
    - 데이터 추가,삭제되어도 안정적
- 단점
    - 특정 구간으로 바로 이동하기 힘듬
    - 순차 탐색만 가능
    - Keyset은 정렬 컬럼으로 조회는 가능하지만, 성능을 얻으려면 정렬/검색 기준 컬럼에 인덱스가 있어야 함
        - 이때 조회 조건(WHERE) + 정렬(ORDER BY) 와 인덱스 방향을 맞춰준다.
    ```java
    WHERE created_at < ?
    ORDER BY created_at DESC, id DESC
    LIMIT 20
    
    ```
